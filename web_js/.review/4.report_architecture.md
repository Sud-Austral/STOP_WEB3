# 🏗️ Reporte de Arquitectura: architecture-reviewer

## 📋 Contexto
Evaluación de la estructura macro del proyecto basada en `.review/0.context_master.md`.

## 🚨 Hallazgos de Arquitectura

### 1. Acoplamiento Fuerte Vistas-Estado Global
**🏗️ Aspecto**: Vistas (`vistas2/*.html`).
**📐 Patrón Detectado**: **Global State Access** Directo.
**⚠️ Riesgo Arquitectónico**: **Acoplamiento / Fragilidad**.
Cada archivo HTML `vistaX.html` contiene lógica Javascript embebida que accede directamente a `window.STATE_DATA.allDataHistory` y `window.COLS`. Esto hace que las vistas sean:
- Difíciles de testear aisladamente (Unit Testing imposible sin mockear `window`).
- Difíciles de reutilizar en otros contextos.
- Susceptibles a romperse si cambia la estructura de `STATE_DATA`.
**📈 Recomendación**: Implementar un patrón **Controller-View** o **Custom Element (Web Components)**.
Las vistas deberían recibir los datos como props o `setContext(data)`, o suscribirse a un Store observable (`DataStore.subscribe(...)`).

### 2. Flujo de Datos Bidireccional Implícito
**🏗️ Aspecto**: `STATE_DATA` mutable.
**📐 Patrón Detectado**: **Acceso Mutable Global**.
**⚠️ Riesgo Arquitectónico**: **Falta de Predictibilidad**.
Cualquier parte de la aplicación puede modificar `STATE_DATA` (ej: `ia2.js` lee datos, pero teóricamente podría escribirlos o mutarlos por error). No hay un **One-Way Data Flow** claro.
**📈 Recomendación**: Usar un patrón **Flux/Redux simplificado** o **Signals** (ej: `DataSignal.value`). Los componentes solo deberían leer el estado y emitir acciones (`DataActions.reload()`), nunca modificar el estado directamente.

### 3. Estrategia de Carga de Módulos (Sync vs Async)
**🏗️ Aspecto**: `index_vistas2.html` `<script src="...">`.
**📐 Patrón Detectado**: **Script Bundling Manual**.
**⚠️ Riesgo Arquitectónico**: **Escalabilidad**.
La lista de scripts crece linealmente (`ia.js`, `ia2.js`, `pdf.js`, `utils/*.js`). El orden de carga es crítico y manual. Si `ia2.js` depende de `utils/chart-enhancer.js`, debe cargarse después. Esto es propenso a errores en equipos grandes.
**📈 Recomendación**: Migrar a **ES Modules (`type="module"`)**. Declarar dependencias explícitas (`import ... from ...`). Eliminaría la necesidad de ordenar scripts manualmente en HTML y permitiría Tree Shaking nativo.

### 4. Lógica de Negocio Dispersa (Python vs JS)
**🏗️ Aspecto**: Cálculos de métricas (Z-Score, Variaciones).
**📐 Patrón Detectado**: **Dual Stack Business Logic**.
**⚠️ Riesgo Arquitectónico**: **Inconsistencia**.
Parte de la lógica reside en `notebook/*.py` (Python, ETL) y parte en `vistas2/*.html` (JS, Presentación). Ejemplo: "Delta Semanal" se calcula en Python (`delta`) pero "Variación Interanual" se recalcula en JS (`v1_var_anual`) usando la fórmula.
Si cambia la definición de "Variación" (ej: manejo de denominador 0), debe cambiarse en ambos lados.
**📈 Recomendación**: Centralizar TODA la lógica de métricas derivadas en Python (exportar JSONs "Listos para Renderizar") o TODA en una librería JS de utilidades (`Metrics.calculateVar(...)`). La primera opción (Python) es preferible para rendimiento Frontend.

## 📉 Recomendaciones Generales
1.  **Migrar a ES Modules**: Priority 1 para modernizar la arquitectura y gestión de dependencias.
2.  **Abstraer Data Access**: Crear un Facade (`DataAdapter.getWeeklyTrends()`) que encapsule la lógica de acceso a `STATE_DATA` y `COLS`, desacoplando las vistas de la estructura interna del JSON.
3.  **Componentización**: Convertir los bloques repetitivos de HTML (KPI cards, headers) en Web Components nativos o funciones generadoras de HTML.
