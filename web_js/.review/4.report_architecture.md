## 1️⃣ ORGANIZACIÓN Y CAPAS

### ARCH-001: Ausencia de Separation of Concerns
**🏗️ Aspecto**: Capa de Vistas

**📐 Patrón Detectado**: Monolithic View (HTML + CSS + JS inline)

**⚠️ Riesgo Arquitectónico**: Las 27 vistas de `vistas2/` mezclan estructura (HTML), presentación (CSS `<style>`) y lógica (JavaScript `<script>`) en un solo archivo. Cada archivo es autónomoexcepto por su dependencia en globals. Esto impide:
- **Linting/Testing** del JS de vista (no es un módulo importable).
- **Reutilización** de componentes entre vistas.
- **Code splitting** o lazy loading selectivo.

**📈 Recomendación**: Separación progresiva. Fase 1: extraer `<script>` a archivos `.js` independientes. Fase 2: evaluar Web Components para componentes repetidos (KPI cards, chart wrappers).

---

### ARCH-002: God Object — `STATE_DATA`
**🏗️ Aspecto**: State Management

**📐 Patrón Detectado**: Global Mutable Singleton

**⚠️ Riesgo Arquitectónico**: `window.STATE_DATA` es un objeto mutable compartido entre ~70 archivos. Cualquier vista puede leer Y modificar el estado sin restricción. No hay inmutabilidad, ni historial de cambios, ni encapsulación.

**Propiedades actuales de STATE_DATA**:
```
codcom, allData, allDataHistory, allDataHistory_total,
stats, currentSection, comunaName, regionName,
semanaId, semanaDetalle, warning, isLoaded,
currentSemana, getFormattedDate, getRaw, ...
```

**📈 Recomendación**:
```javascript
// Fase 1: Freeze para prevenir mutaciones accidentales
Object.freeze(window.STATE_DATA);

// Fase 2: Proxy para logging de accesos
window.STATE_DATA = new Proxy(state, {
    set(target, prop, value) {
        console.warn(`STATE_DATA.${prop} mutated`);
        target[prop] = value;
        return true;
    }
});
```

### ARCH-003: Acoplamiento Directo Vista → Store
**🏗️ Aspecto**: Dependency Direction

**📐 Patrón Detectado**: Direct Access (no Dependency Injection)

**⚠️ Riesgo Arquitectónico**: Cada vista accede directamente a `window.STATE_DATA`, `window.COLS`, `window.STATE_DATA_CEAD`, etc. No existe una capa de servicio o un patrón de inyección. Esto significa:
- Imposible testear una vista con datos mock.
- Imposible cambiar la estructura de datos sin modificar todas las vistas.
- Las vistas conocen la implementación interna del store.

**📈 Recomendación**: Crear un `ViewContext` que cada vista reciba como parámetro:
```javascript
// En App.loadView()
const ctx = {
    stop: window.STATE_DATA,
    cead: window.STATE_DATA_CEAD,
    cols: window.COLS,
    helpers: { getFormattedDate: ... }
};
window._viewContext = ctx; // Temporal, migration step
```

## 2️⃣ FLUJO DE DATOS Y ESTADO

### ARCH-004: Data Flow Bidireccional (Impredecible)
**🏗️ Aspecto**: Data Flow

**📐 Patrón Detectado**: Free-form Mutation

**⚠️ Riesgo Arquitectónico**: El flujo de datos actual es:
```
DataManager → STATE_DATA ← → Vistas
                ↑
            IAModule (lee STATE_DATA para generar contexto IA)
```
Las vistas pueden mutar `STATE_DATA` (ej: cambiar `currentSection`). `IAModule` lee `STATE_DATA` para construir el contexto del prompt. Si una vista modifica el estado antes de que IA lo lea, los resultados serán inconsistentes.

**📈 Recomendación**: Implementar flujo unidireccional:
```
DataManager → STATE_DATA (read-only) → Vistas (solo lectura)
                                       ↓ (eventos)
                                       App (dispatcher)
```

---

### ARCH-005: Dual Event System (Legacy + Custom Events)
**🏗️ Aspecto**: Communication Patterns

**📐 Patrón Detectado**: Hybrid (Polling + Custom Events)

**⚠️ Riesgo Arquitectónico**: Coexisten dos mecanismos de comunicación:
1. **Custom Events** (`dataManagerLoaded`, `dataManagerError`) — usado por `DataManager`.
2. **Polling** (`setTimeout + check isLoaded`) — usado por todas las vistas.

Las vistas ignoran los Custom Events y usan polling. Esto genera:
- 27 timers concurrentes.
- Latencia innecesaria (200ms promedio de polling delay).
- Complejidad para debugging.

**📈 Recomendación**: Migrar vistas a escuchar `dataManagerLoaded`:
```javascript
window.addEventListener('dataManagerLoaded', (e) => {
    initVista1(e.detail);
});
```

## 3️⃣ ESTRATEGIA DE RENDERIZADO Y DOM

### ARCH-006: Template Management — String Concatenation
**🏗️ Aspecto**: Template System

**📐 Patrón Detectado**: Template Literals + innerHTML

**⚠️ Riesgo Arquitectónico**: El HTML se genera mediante template literals y se inyecta con `innerHTML`. No hay:
- Escape automático de datos.
- Diffing (como Virtual DOM).
- Componentes reutilizables.

**📈 Recomendación**: Para un proyecto sin bundler, la mejor alternativa es:
1. **`<template>` elements**: Declarar templates en HTML, clonarlos con JS.
2. **DocumentFragment**: Para listas largas.
3. **Considerar lit-html** (lightweight templating, 5KB) como dependencia mínima.

---

### ARCH-007: Script Execution Strategy — `executeScripts()`
**🏗️ Aspecto**: Code Loading

**📐 Patrón Detectado**: Manual Script Re-hydration

**⚠️ Riesgo Arquitectónico**: `App.executeScripts()` clona manualmente `<script>` tags del HTML cargado. Este patrón:
- No garantiza orden de ejecución entre múltiples scripts.
- No maneja `async`/`defer` correctamente.
- Crea nodos `<script>` huérfanos en el DOM que nunca se limpian.

```javascript
// Actual (app.js:315-329)
executeScripts(container) {
    const scripts = container.querySelectorAll('script');
    scripts.forEach(oldScript => {
        const newScript = document.createElement('script');
        // copia atributos y contenido
        oldScript.parentNode.replaceChild(newScript, oldScript);
    });
}
```

**📈 Recomendación**: Si se migra a archivos JS separados por vista, este mecanismo deja de ser necesario. El `App.loadView()` haría:
```javascript
await import(`./vistas2/js/vista${num}.js`); // ESM dynamic import
```

## 4️⃣ ESCALABILIDAD

### ARCH-008: ~70+ Vistas sin Lazy Loading Inteligente
**🏗️ Aspecto**: Scalability

**📐 Patrón Detectado**: On-demand fetch (cada vista es un fetch individual)

**⚠️ Riesgo Arquitectónico**: Aunque cada vista se carga bajo demanda (bien), el `DataManager` carga **todos** los datos al inicio (STOP + CEAD + Comunas + Cluster). Para una app con 70+ vistas donde un usuario típico visita ~5-10, se cargan datos innecesarios.

**📈 Recomendación**: 
- Lazy-load `COMUNAS_DATA` solo cuando el usuario accede a vista26/27.
- Lazy-load CEAD data solo cuando se navega a vistas CEAD (21+).

---

### ARCH-009: Ausencia de Error Boundaries
**🏗️ Aspecto**: Fault Tolerance

**📐 Patrón Detectado**: None (fail-open)

**⚠️ Riesgo Arquitectónico**: Si una vista falla durante su IIFE (ej: `TypeError`), el error se traga silenciosamente. No hay mecanismo para:
- Mostrar un fallback UI ("Esta vista no pudo cargar").
- Reportar el error a un servicio de monitoreo.
- Reintentar la carga.

**📈 Recomendación**: Envolver `executeScripts` en try/catch con UI de error:
```javascript
try {
    this.executeScripts(container);
} catch (e) {
    container.innerHTML = `<div class="error-boundary">
        <p>Error al cargar esta vista.</p>
        <button onclick="App.loadView('${viewName}')">Reintentar</button>
    </div>`;
    console.error(`[Vista ${viewName}]`, e);
}
```
