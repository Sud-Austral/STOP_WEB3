# 📘 CONTEXTO MAESTRO: STOP WEB 3 (RID SIMULATOR)

## 📋 METADATA
- **Fecha**: 2026-02-16
- **Stack**: Vanilla JS (ES2020+), Python (ETL Data Processing), CSS3 (Variables + Utility classes)
- **Browser Support**: Modern Browsers (Chrome/Edge/Firefox/Safari evergreen). No legacy IE11 context detected (uses arrow functions, async/await, template literals natively).
- **Criticidad**: ALTA. Herramienta de inteligencia y visualización para seguridad pública. Precisión de datos y disponibilidad son críticas.

## 🎯 OBJETIVOS DE NEGOCIO
Proveer un dashboard de inteligencia delictual ("RID Simulator") que permite a analistas y tomadores de decisiones visualizar, proyectar y analizar tendencias criminales (STOP y CEAD).
El sistema debe transformar datos crudos complejos (Excel/CSV de Carabineros/SPD) en visualizaciones estratégicas claras, permitiendo análisis predictivo (SARIMA), comparativo (Rankings) y detección de anomalías (Z-Score) en tiempo real o pre-calculado.

## 🏗️ ARQUITECTURA TÉCNICA
- **Patrón**: **Global Namespace / Singleton**. Uso extensivo de objetos globales (`window.STATE_DATA`, `window.App`, `window.DataManager`) para gestión de estado.
- **Flujo de Datos (ETL)**:
    1.  **Python (`notebook/*.py`)**: Ingesta, limpieza, normalización y cálculo estadístico pesado (SARIMA, Z-Scores) desde fuentes CSV/Excel. Generación de JSONs estáticos (`data/*.json`, `data/cead_split/*.json`).
    2.  **Frontend (`js/data_manager.js`)**: Carga asíncrona (`fetch`) de JSONs, descompresión (gzip opcional stream) y unificación en memoria (`STATE_DATA`).
    3.  **Render (`vistas2/*.html` + `js/app.js`)**: Inyección directa de HTML/JS en el DOM. Cada "vista" actúa como un componente cuasi-independiente que consume el estado global.
- **Web Standards Compliance**: Alto uso de estándares modernos (Fetch API, Promises, CSS Variables). Bajo acoplamiento con librerías de UI (sin React/Vue), pero dependencia fuerte de librerías de visualización (`Chart.js`, `Leaflet`).
- **Restricciones de Entorno**:
    - **Client-side Heavy**: Todo el procesamiento post-carga ocurre en el navegador del cliente.
    - **No-Backend Logic**: El "backend" es estático (archivos JSON servidos). La lógica de negocio está dividida entre el pre-proceso Python y el cliente JS.
    - **CORS/API**: Consumo de APIs externas para IA (`js/ia2.js`) requiere manejo de claves y proxy o CORS permisivo.

## ⚠️ RESTRICCIONES Y ÁREAS SENSIBLES
- **Archivos Críticos**:
    - `notebook/proceso.py` y `notebook/proceso_cead.py`: Corazón del ETL. Cualquier cambio aquí rompe el contrato de datos con el frontend.
    - `js/data_manager.js`: Punto único de fallo para la carga de datos.
    - `js/config/columns.js` y `js/data.js`: Mapeos de columnas. Deben estar sincronizados con la salida de Python.
- **Deuda Técnica**:
    - **Global State Mutation**: El estado es mutable y accesible desde cualquier punto, dificultando el rastreo de cambios.
    - **Hardcoded Views**: Las vistas (`vista1`...`vista25`) tienen lógica duplicada y scripts embebidos, dificultando el mantenimiento masivo.
    - **Inconsistencia de Datos (Python vs JS)**: Lógica de negocio (ej: nombres de delitos, agrupaciones) duplicada o dispersa entre Python y JS.
    - **Manejo de Errores**: Silenciamiento de errores en promesas o cargas de datos parciales.
